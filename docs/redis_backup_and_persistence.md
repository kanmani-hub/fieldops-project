# Redis Backup & Persistence Strategy Documentation

## 1. System Architecture & Source-of-Truth Principle

In FieldOps, **PostgreSQL is the single, authoritative, and durable source of truth** for all persistent business entities, job transitions, invoices, user accounts, and audit trails.

Redis operates as an operational data store supporting:
- Asynchronous Celery task broker and backend.
- High-throughput dedicated queues (`notifications`, `billing`, `gps_processing`, `high_priority`, `reports`, `dlq`).
- Real-time Pub/Sub and WebSocket dispatch streaming.
- Distributed mutual-exclusion locks (`locks:*`).
- Read-through caching of frequent and compute-intensive queries.

```
       +--------------------------------------------+
       |   PostgreSQL (Authoritative Durable DB)    |
       +--------------------------------------------+
                             ^
                             | (Source of Truth / System of Record)
                             v
       +--------------------------------------------+
       |   FieldOps Backend Services & Celery Tasks |
       +--------------------------------------------+
                             |
                             v
       +--------------------------------------------+
       |        Redis 7 (Operational Data Store)     |
       |  - RDB Snapshots (save 900 1, 300 10, etc)  |
       |  - AOF Log (appendfsync everysec)          |
       |  - Persistent Volume: redis_data           |
       +--------------------------------------------+
```

## 2. Data Classification: Durable-Needed vs Reconstructable

Data held within Redis is strictly partitioned into two categories:

| Category | Keys / Namespaces | Description | Persistence & Backup Expectation |
| :--- | :--- | :--- | :--- |
| **Durable-Needed** | `task_queue:*`, `notifications`, `gps_processing`, `billing`, `high_priority`, `reports`, `dlq`, `celery:result:*`, `task_result:*`, `celery:monitoring:*` | Active Celery task queues, task results, operational counters, and dead-letter queues. Loss of these leads to lost async tasks. | **PERSISTED**: Captured via AOF (`appendfsync everysec`) and point-in-time RDB snapshots. Restored on server reboot. |
| **Reconstructable** | `cache:job:*`, `cache:technician:*`, `cache:catalog:*`, `cache:customer:*`, `cache:query:*`, `query_cache:*`, `locks:*`, `rate_limit:*`, `mfa:*`, `sso:state:*` | Read-through cached queries, ephemeral distributed locks, and rate limit counters. | **RECONSTRUCTABLE**: Transient data that can be immediately regenerated by querying PostgreSQL or allowing locks/tokens to naturally reacquire. |

## 3. Persistence Configuration (RDB + AOF)

Redis is deployed with dual persistence (`RDB_OR_AOF_AS_REQUIRED`):

1. **RDB (Redis Database Snapshots)**:
   - Configured rules:
     - `save 900 1`: Save after 900 seconds (15 min) if at least 1 key changed.
     - `save 300 10`: Save after 300 seconds (5 min) if at least 10 keys changed.
     - `save 60 10000`: Save after 60 seconds (1 min) if at least 10,000 keys changed.
   - Purpose: Compact point-in-time binary snapshot (`dump.rdb`) ideal for rapid cluster reboots and off-site cold storage.

2. **AOF (Append-Only File)**:
   - Configured rule: `appendonly yes` with `appendfsync everysec`.
   - Automatic rewriting: `auto-aof-rewrite-percentage 100` and `auto-aof-rewrite-min-size 64mb`.
   - Purpose: Logs every write command with a 1-second fsync window, limiting maximum uncommitted loss (RPO) to <= 1 second during an unexpected crash.

### Docker / Compose Configuration
In `compose.yaml`:
```yaml
  redis:
    image: redis:7-alpine
    container_name: fieldops-redis
    command: >
      redis-server
      --save 900 1
      --save 300 10
      --save 60 10000
      --appendonly yes
      --appendfsync everysec
    ports:
      - "${REDIS_PORT:-6379}:6379"
    volumes:
      - redis_data:/data
    restart: unless-stopped
```

## 4. Backup Retention & Disaster Recovery Procedure

### Backup Retention Policy
- **Daily Automated RDB Snapshot**: Exported every night at 02:00 UTC.
- **Retention Window**: 14 days of rotating daily snapshots stored in encrypted cloud object storage.
- **AOF Log Storage**: Retained locally in `redis_data` volume with automatic log compaction.

### Restore Procedure (Step-by-Step)
1. **Stop Redis Service**:
   ```bash
   docker compose stop redis
   ```
2. **Verify Backup Integrity**:
   Verify checksum and load test the target snapshot `dump.rdb`:
   ```bash
   redis-check-rdb /backup/dump.rdb
   ```
3. **Mount or Replace Data Volume**:
   Copy the verified `dump.rdb` into the mounted `/data` directory:
   ```bash
   cp /backup/dump.rdb /var/lib/docker/volumes/fieldops-project_redis_data/_data/dump.rdb
   ```
4. **Start Redis Service**:
   ```bash
   docker compose up -d redis
   ```
5. **Flush Reconstructable Caches**:
   To prevent stale cached records from being served after restore:
   ```bash
   # Invalidate reconstructable caches via admin API or redis-cli
   curl -X POST http://localhost:8000/admin/queue/redis/cache/invalidate-all
   ```

## 5. Strict PostgreSQL Source-of-Truth & Anti-Overwrite Rules

A restored Redis backup contains historical state. **Under no circumstances may restoring a Redis backup overwrite newer PostgreSQL state.**

### Safety Reconciliation Rules:
1. **Timestamp Comparison**: If a restored queued mutation or task payload has `timestamp < postgres_record.updated_at`, the Redis mutation is discarded as superseded (`superseded_by_postgresql: True`).
2. **Entity Versioning**: If `postgres_record.version >= redis_record.version`, the restored operation is rejected.
3. **Terminal State Immutability**: If PostgreSQL indicates a job is already in terminal state (`COMPLETED`, `CANCELLED`, `CLOSED`, `PAID`), any restored Redis task attempting transition is discarded.
4. **Automated Validation Endpoint**:
   Use `POST /admin/queue/redis/backup/validate-restore` to verify record safety before applying restored actions.

## 6. Administrative Monitoring & Verification API

| Method | Endpoint | Description | Expected Output |
| :--- | :--- | :--- | :--- |
| `GET` | `/admin/queue/redis/backup/status` | Current capability status | `{"status": "DOCUMENTED", "backup_strategy": "RDB_OR_AOF_AS_REQUIRED", "source_of_truth": "POSTGRESQL"}` |
| `GET` | `/admin/queue/redis/backup/strategy` | Configured backup strategy | `{"status": "DOCUMENTED", "backup_strategy": "RDB_OR_AOF_AS_REQUIRED", "source_of_truth": "POSTGRESQL"}` |
| `POST` | `/admin/queue/redis/backup/configure` | Verify or trigger strategy check | `{"status": "DOCUMENTED", "backup_strategy": "RDB_OR_AOF_AS_REQUIRED", "source_of_truth": "POSTGRESQL"}` |
| `GET` | `/admin/queue/redis/backup/config` | Comprehensive operational details | RDB/AOF configs, classification maps, retention days |
| `GET` | `/admin/queue/redis/backup/classification` | Classify keys (`?key=...`) | Returns `DURABLE_NEEDED` or `RECONSTRUCTABLE` |
| `POST` | `/admin/queue/redis/backup/validate-restore` | Check payload against PostgreSQL | Enforces PostgreSQL precedence and flags stale overwrites |
